Phase 1: Foundations & Motivations

Verification vs. Validation

Understanding testing starts with two crucial questions:

  • Verification: "Are we building the product right?" (Does the code match the design documents?)
  • Validation: "Are we building the right product?" (Does this actually solve the user's real-world problem?)

The Cost of Quality

We test to identify defects early. Why? Because of the Rule of 10. A bug found during requirements gathering costs $1 to fix. During coding, $10. After release to the public? $100+ and your reputation.

Key Definitions

  • Error: A human mistake (e.g., developer misunderstands a rule).
  • Defect (Bug): The physical flaw injected into the code.
  • Failure: The system crashing when the user clicks a button.

Phase 2: Strategy & Requirements

The Traceability Matrix

How do you know you've tested everything? You use a Requirements Traceability Matrix (RTM). It is a document that maps every single user requirement to a specific Test Case, ensuring 100% coverage.

Anatomy of a Test Case

A professional test case isn't just "try logging in." It includes:

  • Pre-conditions: User must have an active account.
  • Test Data: Username: test@test.com, Pass: 12345.
  • Execution Steps: 1. Navigate to /login. 2. Enter credentials. 3. Click Submit.
  • Expected Result: User is redirected to Dashboard.
  • Actual Result: (Filled during execution).

Phase 3: Levels and Types of Testing

The Testing V-Model Levels

  • Unit Testing: Testing a single isolated function (White Box).
  • Integration Testing: Ensuring Module A talks correctly to Module B.
  • System Testing: Testing the entire compiled application end-to-end (Black Box).
  • Acceptance Testing (UAT): The client testing the app to sign off on the release.

Smoke vs. Sanity Testing

Smoke Testing: A quick test to see if the main features work (e.g., does the app even start?). If it fails, reject the build.
Sanity Testing: Deep testing of a specific module after a minor code change to ensure the bug is actually fixed.

Phase 4: Practical JUnit & TDD

Test Driven Development (TDD)

TDD reverses standard coding. You write the Test first. It will fail (Red). Then you write the minimum code to pass it (Green). Then you clean up the code (Refactor).

Advanced JUnit & Mockito

Sometimes you need to test a function that relies on a database, but the database isn't built yet. We use Stubs and Mocks (like the Mockito framework) to create "fake" databases that return fixed answers, allowing us to test our logic in total isolation.

@Test
void testLogin() {
    // Mocking the database response
    when(mockDB.getUser("john")).thenReturn(validUser);
    
    // Asserting the logic
    assertTrue(authService.login("john", "pass"));
}

Phase 5: Execution & Career Growth

The CI/CD Pipeline

Modern testers don't click buttons manually all day. They integrate automated tests into Continuous Integration (CI) pipelines (like Jenkins or GitHub Actions). Every time a developer saves code, your automated tests run in the cloud instantly.

Writing the Perfect Bug Report

To prevent developers from saying "Works on my machine," include:

  • Exact Environment (Chrome 114, Windows 11).
  • Clear "Steps to Reproduce".
  • Screenshots, video recordings, and console logs.

Phase 6: Future Trends

Shift-Left & Automation

The industry is moving towards Shift-Left testing—testing during the design phase before code is written. For automation, tools like Selenium, Cypress, and Playwright are industry standards for simulating a real user clicking through a web browser.

AI in Testing

Artificial Intelligence is now being used for "Self-healing tests" (if a developer changes a button's ID, the AI finds the new button automatically) and auto-generating test scripts based on analyzing user behavior in production.
